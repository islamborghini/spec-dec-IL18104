Speculative decoding speeds up language generation by letting a smaller model propose tokens and asking a larger model to verify them. The smaller model is called the drafter, and the larger model is called the target. The aim is to produce the target model's output with fewer sequential target calls. The target remains responsible for deciding which proposed tokens are valid. This explanation is authored demonstration text, not an output recorded from either model.

A standard autoregressive model generates one token at a time. It reads the available context, computes scores for the next token, selects a token, and repeats the process. Even with a key-value cache, every new token needs another forward pass through the model. These sequential calls are an important source of latency. A powerful GPU may have spare compute capacity during a single-token step, but the next step still depends on the token that was just selected.

Speculative decoding changes the schedule of that work. The drafter predicts several tokens in sequence. The target then processes the proposed block in one verification pass. Because all the proposed tokens are already available, the target can compute predictions for their positions together. When several consecutive proposals match what the target would produce, the algorithm makes progress by several tokens while using only one target verification pass.

In our project, the target is Qwen3-4B and the drafter is Qwen3-0.6B. We implemented greedy speculative decoding, where tokens are selected by their highest score. The verifier accepts the consecutive matching prefix of the draft. At the first disagreement, it emits the target's correction. If the entire block matches, it can emit an additional target token. Both paths reuse key-value caches rather than recomputing the complete context at every iteration.

The draft length, often written as k, controls how many proposals are made before verification. A larger k offers more potential progress per target pass, but it also requires more serial drafter calls. It can waste work when the target rejects an early proposal. A smaller k spends less time drafting but verifies more frequently. The best value therefore depends on the actual execution cost and how often the draft agrees with the target.

Acceptance rate measures retained draft tokens divided by the number of proposals. It is useful, but it is not a speed measurement. Two systems can have the same acceptance rate and very different latency. A drafter that takes a long time to make its proposals may spend more time than it saves. The number of output tokens per target verification is another useful metric, because it includes the correction or bonus token as well as accepted proposals.

The central timing tradeoff is straightforward. A speculative round must pay for drafting, target verification, and the surrounding cache and selection work. That round needs to produce enough output to cost less than generating those tokens directly with the target. Reducing the number of target calls helps only when the replacement work is sufficiently cheap. Speculative decoding is an execution strategy, not a guarantee that every pair of models becomes faster.

We trained the drafter with probability distillation. The target's parameters stayed frozen, while small LoRA adapters changed the drafter. Both models received the same text prefixes, and the loss encouraged their next-token distributions to match. Specifically, we minimized the KL divergence from the target distribution to the drafter distribution. This differs from comparing completed paragraphs with cosine similarity, because it works directly with next-token probabilities at each position.

Training used WikiText chunks with 256 tokens each. The preparation pipeline preserved the official evaluation splits and recorded source articles, token offsets, random seeds, and checksums. For the final continuation, it selected fresh windows that did not overlap earlier training spans. It also rejected duplicate windows and shared 32-token passages with the held-out material. The purpose was to add varied text without recycling the chunks already used in previous training phases.

The full training history reached 10,000 optimizer updates. An optimizer update combined gradients from four chunks, so an update is not the same thing as a chunk. The initial pilot used 125 updates, followed by a larger phase reaching update 2,625. The final phase added 7,375 updates using 29,500 new chunks. We continued the same experiment history rather than presenting those phases as unrelated runs.

Validation loss improved substantially over the complete training history. KL started near 1.065 with the original drafter and reached about 0.724 at the selected checkpoint. The best validation checkpoint was update 9,875, rather than the final update at 10,000. This is why the inference comparison uses the selected model. Validation was used for checkpoint selection, while the reserved final test generations remained unused.

The generation comparison measured the target alone, the original speculative drafter, the earlier trained checkpoint, and the newly selected checkpoint in the same A10 job. All methods received the same validation prompts. We repeated the timings and rotated the order so that one method did not always run first. Model loading and warm-up were outside the timed region, while the generation timing included both models' work and cache management.

At four proposals per verification, the original drafter achieved approximately 21.4 output tokens per second. The selected trained drafter achieved approximately 24.2 tokens per second. Acceptance increased from about 42 percent to 51 percent. Those measurements show an improvement over the original drafter. However, the target alone achieved approximately 33.0 tokens per second in the same job, so the trained speculative system still did not produce a net acceleration over that baseline.

Additional training beyond the earlier checkpoint had smaller effects. The checkpoint at update 2,625 achieved approximately 23.9 tokens per second, compared with 24.2 for the selected later checkpoint. This is a modest difference on a limited validation benchmark. It should not be turned into a broad claim that further training can never help. It instead suggests diminishing returns for the particular training objective, adapter configuration, data, and inference implementation that we measured.

We also tested different draft lengths using the selected trained model. The sweep compared k values of one, two, four, and eight on the same validation prompts. In that separate experiment, one proposal per verification was fastest at about 29.2 tokens per second. Four proposals reached about 24.5, while eight reached about 17.8. The target-only baseline in that sweep was about 33.7. These are results from a separate job and should be compared within that job.

This behavior illustrates why more proposals are not automatically better. Increasing the draft length raised output tokens per verification, but it added so much drafting work that throughput fell. The larger block was more effective at reducing the frequency of target verification, yet less effective at reducing total time. A latency optimization must account for both sides of that tradeoff instead of optimizing one intermediate metric in isolation.

The earlier timing breakdown assigned most of the observed decoding time to drafter forward calls. The drafter has fewer parameters, but it still has 28 transformer layers, compared with 36 in the target. A small parameter count does not guarantee a proportionally shorter single-token call. Work inside model execution can include memory traffic, many kernel launches, and computation. A deeper kernel trace would be needed to separate those effects rather than attributing all of the time to one cause.

There is also a numerical limitation. Some BF16 speculative continuations differed from target-only continuations. Near-tied scores can lead to different greedy choices when calculations use different shapes, after which the generated sequences diverge. We therefore report the mismatches and do not claim a verified lossless speedup. Similar-looking paragraphs would not be enough to establish token-level equivalence, and a faster mismatching sequence would not solve the correctness requirement.

The benchmark itself has limits. It uses short contexts and short outputs on a small set of validation articles. Some generated text is repetitive, including a case that produces repeated equals signs. Such a case can make agreement look unusually strong. Repeated timings help characterize execution variation, but they do not create additional independent articles. A final performance claim needs a broader evaluation design, explicit numerical controls, and results on the reserved test set after settings have been frozen.

For the progress report, the important result is that the entire pipeline works and can be inspected. We can trace prepared data into training, observe the loss curves, restore checkpoints, compare baselines, and identify limitations in the measured speed. The experiments show that training improved drafter agreement while the execution cost still prevented a net speedup. The next work is to test cheaper drafting and stronger inference controls while keeping the comparison fair to the target-only baseline.

It is useful to distinguish the model from the software that runs it. The same weights can be executed by different inference implementations. A serving engine may reduce overhead with compilation, specialized kernels, or captured GPU execution. Such a change is still an inference experiment, and it should be evaluated with both the target-only and speculative paths using the same engine. Otherwise an improvement could come from comparing different software implementations rather than from speculation itself.

A sound comparison should also separate model loading from generation. Loading several gigabytes of weights is expensive, but it is not the repeated operation that speculative decoding aims to accelerate. In a resident-model benchmark, weights are already available and both paths receive an initial warm-up. The timer then measures the work needed to produce the output. If a future application includes cold starts, those costs should be measured and reported separately instead of silently mixing them into token-generation throughput.

Prompt length, output length, and concurrency can change the tradeoff. A method that is useful for one long response at batch size one might behave differently when many requests share a GPU. A short-answer benchmark can be affected more strongly by prefill or final partially used blocks. Longer contexts increase attention and cache costs. These differences are reasons to state the exact workload rather than treating one tokens-per-second number as a universal property of a model.

Reproducibility is equally important. The project keeps the tokenizer and model revisions fixed, records prepared data checksums, and preserves each experiment's configuration. Saved raw records allow comparisons to be inspected without rerunning the expensive part of the pipeline. They also make it possible to revisit an interpretation when a new experiment disagrees with an earlier one. Historical measurements remain useful when their conditions and limitations are kept visible.
